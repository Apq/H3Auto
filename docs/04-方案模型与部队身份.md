## 4. 数据结构（PolicyCore 定义 / ConfigLog 驻留状态）

<a id="section-4-1"></a>
### 4.1 枚举

```cpp
enum AutoActionKind {         // 行动类型
    AA_MANUAL = 0,            // 手动（不接管）
    AA_DEFEND = 1,            // 防御
    AA_WAIT = 2,              // 等待（保留占位，UI 已隐藏）
    AA_MOVE = 3,              // 循环移动
    AA_MELEE_ATTACK = 4,      // 循环近战（枚举值保持不变）
    AA_RANGED_ATTACK = 5,     // 远程攻击
    AA_FIRST_AID = 6,         // 急救
    AA_SCATTER = 7,           // 散开（仅召唤物共享规则可选）
    AA_RANDOM_MOVE = 8,       // 随机移动（仅召唤物共享规则可选）
};

enum AutoTargetSide {         // 目标阵营
    ATS_OWN = 0,              // 己方
    ATS_ENEMY = 1,            // 敌方
    ATS_EITHER = 2,           // 双方
};

enum AutoTargetSelector {     // 按行动分流
    SEL_RANDOM = 0,           // 随机（远程/急救）
    SEL_RANGED_SPEED = 1,     // 远程：远程速度优先
    SEL_COUNT_HIGH = 2,       // 远程：数量最多
    SEL_WOUND_RATIO = 3,      // 急救：失血比例最高
    SEL_WOUND_VALUE = 4,      // 急救：失血数值最大
};
```

> 行动/目标标签由 `LoadUiTexts` 从 lang 文件 `[actions]/[selectors]` 序号键填充（[§16.1](<08-配置与界面文案.md#section-16-1>)），内置默认数组兜底。目标阵营下拉已停用，阵营由各行动固定。

<a id="section-4-2"></a>
### 4.2 规则结构

```cpp
struct AutoTargetRule {
    AutoTargetKind   kind;             // 目标类型（无 / 部队 / 位置）
    AutoTargetSide   side;             // 目标阵营
    AutoTargetSelector selector;       // 选择器
    int16_t          meleeStandHex;    // 旧版单组近战兼容镜像
    int16_t          meleeAttackHex;   // 旧版单组近战兼容镜像
    int16_t          moveWaypoints[16]; // 循环移动: 路径点列表（最多 16）
    int8_t           moveWaypointCount;  // 有效路径点数
    int16_t          meleeStandHexes[10]; // 循环近战: 各组站立位
    int16_t          meleeAttackHexes[10];// 循环近战: 各组攻击位
    int8_t           meleePairCount;     // 有效组合数
};

struct AutoStackRule {
    AutoActionKind  action;              // 行动类型
    AutoTargetRule  target;              // 目标规则
    bool            allowDefendFallback; // 无法执行时是否降级为防御
    bool            quickCastFirst;      // 兼容：spellSlotCount>0 时为 true
    int8_t          spellSlot;           // 兼容镜像：等于 spellSlots[0]（1-9/0）
    int8_t          spellSlots[10];      // 循环施法快捷键序列（单行最多 10 槽）
    int8_t          spellSlotCount;      // 有效槽位数 0..10

    // 保活（§3.1.1）：挂单支部队，随方案/槽位一起存储与重排。
    uint8_t         protectMode;         // ProtectMode：0=按剩余数量；1=损失量大于恢复量；2=不保活（默认）
int             protectCountBelow;   // 按数量阈值：剩余数量 ≤ 此值才救（默认 2，仅 PM_COUNT_BELOW 显示）
};
```

### 4.3 方案存储

```cpp
AutoStackRule g_profiles[5][21];      // 5 套方案草稿 × 21 槽位，仅驻留内存（切换编号不丢）
int          g_active_profile;       // 当前生效方案编号（勾号时 = 选中编号）
AutoStackRule g_active_rules[21];     // 当前生效规则（生效方案运行时视图 = g_profiles[g_active_profile]；执行端读取，保活方式随槽位规则走）
int          g_last_profile;        // 上次勾号生效槽位（user.ini [General] LastProfile 持久化）
uint16_t     g_stop_turns[5];        // 方案级自动停止阈值（0..999，默认 4，0=关闭）
SummonProfileFields g_summon[5];     // 方案级召唤参数（enabled 启用位、队数/血量阈值、
                                     // 条件组合、法术选择、敌方魔力停止勾选+阈值、召唤物共享规则）
StatusProfileFields g_status[5];     // 方案级保持状态列表（slots[8] 已选法术 id、
                                     // slot_count、slow 单独开关（int，非 bool）；§3.1.3/§8.9）
// SummonProfileFields { enabled=0(默认不启用; 保活优先、无人可救才召唤),
//                       count_th=2, hp_th=750, spell_pick=0(自动/1..4固定),
//                       cond_combine=0(和，默认/1=或),
//                       stop_enemy_mana=1(默认勾), stop_mana_th=6,
//                       summon_rule(AutoStackRule, action=AA_DEFEND 默认防御) }
```

驻留初始化：`g_profiles`/`g_active_rules` 由同 TU 静态初始化器（`DefaultRulesInit_`，定义于两数组之后、先于任何钩子执行）回填 `MakeDefaultRule()`——保活方式为 `PM_NONE`（不保活）、「剩≤」阈值 2 等默认值自 DLL 载入即成立，不依赖首次 `ClearConfirmedProfiles` 或存读档；修复前 `= {}` 全零会在启动后首开面板时显示「剩≤0」并随勾号固化。

<a id="section-4-4"></a>
### 4.4 当前战斗部队跟踪

玩家提交设置后，执行端会绑定本场人类侧部队跟踪表（`g_stack_track[21]`）：

- **配置身份**：普通开战部队使用 `side + source_army_slot`；战争机器使用“类型 + 同类序号”。
- **当前定位**：`side + army_slot_ix` 只表示本轮战斗中的数组槽位；`_BattleStack_` 指针也只表示当前数组单元，不能跨重打使用。
- **运行刷新**：存活（`count_current>0`）、位置（`hex_ix`）、数量（`count_current`）
- **执行前置**：只有活动单位通过跟踪校验时才套用 `g_active_rules[slot]`
- **动态部队**：召唤物和克隆物有本场内身份（`STACK_ID_SUMMON`：类型 + 同类出现序号），身份可用于本场校验；实际接管只对启用召唤时的四系召唤物使用共享规则，克隆保持手动。克隆体先按 `clone_id>0` 判定，避免继承本体的军队槽身份。召唤启用（`g_summon[p].enabled`）时，`UpdateStackTracking_` 每次行动对未绑定槽做动态补绑：四系元素（`IsSummonedElemental`）+ 存活 → 绑定跟踪条目并套用 `g_summon[p].summon_rule` 共享规则，此后走现有行动管线（[§3.7](<03-英雄施法与自动停止.md#section-3-7>)）；克隆物与其他衍生单位不补绑、保持手动。
- **失效条件**：身份不匹配、死亡后槽位被复用、非人类侧、未绑定

这样避免“只按槽位索引取规则”导致的错套：敌方同槽、死亡后槽复用、同兵种召唤物复用，以及跨侧活动单位。

<a id="section-4-5"></a>
### 4.5 快速战斗重打的身份重建

原版和 HD 的战斗管理器通常复用同一个 `H3CombatManager` 及其 `stack[2][21]` 固定数组。取消快速战斗后，物理地址可能不变，但数组单元中的逻辑部队会按战前军队快照重新初始化。因此指针相同不代表仍是同一支逻辑部队。

取消重打回到 BattleUI 时，`EnsureStackTrackingBound` 执行以下顺序：

1. 扫描新战场并生成稳定身份。
2. 将 5 套方案从旧战场槽重排到新战场槽；找不到对应身份的槽使用默认规则。保活方式（`protectMode`）在 `AutoStackRule` 内，随槽位规则整体一起重排；召唤启用位与召唤参数是方案级不参与重排（`g_summon[5]`）。
3. 保留方案，清除旧的活动部队指针、施法等待、动作唤醒和单次接管状态。
4. 重置本轮移动、近战、施法游标，递增战斗尝试代次。
5. 以新战场对象重新建立 `g_stack_track[21]`。

接受结果才调用 `OnBattleResultAccepted`，清除 5 套方案；取消重打不会清除方案（`g_last_profile` 也不清，跨战斗保留）。

稳定身份的适用范围：

- `source_army_slot` 适用于原英雄/军队中的 0 到 6 号开战部队。
- 战争机器没有通用原军队槽，使用类型和同类序号。
- 召唤物、克隆物以及其他 `source_army_slot=-1` 的衍生对象没有跨重打身份：本场内按 `STACK_ID_SUMMON` 跟踪执行，重排（`BuildStableStackSlotRemap`）明确跳过该类身份，重打后回到默认规则。

## 9. 方案保存流程

目标行为：打开界面自动加载上次设置；调整过程中不影响已保存设置；仅点「确定（勾✓）」才真正写入。

- 打开面板：`g_profiles → s_p.draft_rules`，进入草稿副本编辑，原方案不动。
- 编辑格子：改动只写 `s_p.cells[].data.rule`（内存草稿）。
- 切换方案（`SelectProfile_`）：先 `SaveCurrentCellsToDraft_` 存回草稿，再 `LoadSelectedProfileIntoCells_` 载入目标方案。
- 点确定（`CommitAndCloseSettingsPanel_`）：`SaveCurrentCellsToDraft_` → `CommitProfiles` 一次性提交全部 5 套到 `g_profiles`，选中编号立即生效。
- 点取消 / ESC：直接关闭，草稿丢弃。

<a id="section-9-1"></a>
### 9.1 设置生命周期（锚定「一场战斗」）

设置只对**当前这场战斗**有效，生命周期以「玩家接受战斗结果」为终点，而非战斗动画打完：

1. 设置在面板确定后写入 `g_profiles` / `g_active_rules`，整场（含重打）常驻内存。
2. **重打不算新战斗**：结果窗出现后点 HD「取消/重打」（控件 id `0x1FB`）→ 方案保留；BattleUI 回来后状态机重打边（`BE_RESULT_RETRY`）触发 `EnsureStackTrackingBound` 按稳定身份重排方案、清理本轮运行态并强制重绑跟踪；控制权**切回全手动**（2026-10-06 修正：原为保留进场前模式；上一场 AUTO 中重打会残留 AUTO，一进战斗没按 F9 就自动打）。
3. 反复重打仍是同一场，设置一路保留。
4. **点结果窗「确定/接受」**（控件 id `0x7802` / iOkay）→ 状态机 `BE_RESULT_ACCEPTED` 边：清空 5 套方案 + 运行时状态 + 跟踪，控制权回**全手动**（2026-10-06 修正：原为回自动；自动只能由 F9 显式启动，进场不默认自动）；**面板草稿（5 套规则/停止/召唤参数/保持状态列表）同步清空**（`ResetPanelDrafts`，由 `ClearConfirmedProfiles` 调用）——修复前草稿驻留会让下一场打开面板仍显示上一场部队的旧规则、点「确定」后旧规则复活生效。下一场想沿用配置走本场存档下拉（[§17](<07-战斗指纹与方案存档.md#section-17>)，四轮关联按类型+数量对位）。`OnBattleResultAccepted` 保留为兼容外壳，实际清理在边动作里。
5. 无取消按钮的纯原版结果窗：结果窗消失且未点取消 → 视为接受并清除。
6. **兜底边**：战斗 UI 消失且未经过结算（战斗中/结算中读档、退主菜单）→ `BE_BATTLE_UI_GONE` 同样清运行时与跟踪，但 5 套方案保留；取消重打后 UI 重建常超过 3 帧检测窗，重打边置 3000ms 宽限防误触。
7. 实现：每帧检测虚表 `0x0063D46C`（CPResult）的出现/消失与按钮命中（`CheckBattleResultLifecycle_`），生命周期事件汇成 `BE_RESULT_SHOWN / RETRY / ACCEPTED` 三条边交给状态机（[§15](<05-战斗生命周期与控制权.md#section-15>)）。

## 力盾方案字段
